interview prep · database fundamentals

Normalization means two
different things.

Same word, two technical concepts. Say the wrong one in an interview and it's marked incorrect — even though you understand the idea perfectly well.

DBMS normalization

Table structure

Organizing tables and columns to remove duplicate data and protect data integrity. Splits one messy table into smaller, related tables linked by foreign keys.

Data normalization

Value formatting

Transforming messy, inconsistent input into one clean, standard format — so equal things look equal, and your code can compare or de-duplicate them.

Data normalization, in practice

what you actually did
instagram.com/p/xyz?igsh=abc123 → instagram.com/p/xyz
Jane.Doe@Email.com → jane.doe@email.com
" Jane Doe " → "Jane Doe"

DBMS normalization: the normal forms

levels of strictness, not a table count
1NF

First Normal Form — the single-value rule

Every cell holds exactly one piece of data. Atomicity.

A "Skills" column can't hold a list like React, Node, Firebase. Break it into separate rows or a separate table so each cell holds one value.

not 1NFSkills: React, Node, Firebase
1NFone skill per row
2NF

Second Normal Form — the whole-key rule

Passes 1NF, and every column depends on the entire primary key — no partial dependencies.

If the primary key is StudentID + CourseID, a StudentName column only depends on StudentID. That's a partial dependency — move it into its own Students table.

violationStudentName depends on half the key
fixStudentName moves to Students table
3NF

Third Normal Form — the no-middleman rule

Passes 2NF, and no non-key column depends on another non-key column — no transitive dependencies.

DepartmentLocation depends on DepartmentName, not on EmployeeID. Split it into a separate Departments table.

violationDeptLocation depends on DeptName
fixDepartments table holds Name + Location

What to say, out loud

the interview answer

"In the context of this specific code, I am referring to Data Normalization — stripping the tracking parameters off the Instagram URLs so they are standardized and my database can catch duplicates.

However, if you are asking about DBMS Normalization, that is different — that is the process of structuring relational tables to eliminate data redundancy, using normal forms like 1NF, 2NF, and 3NF."

The one-breath version

memorize this

Normalization is a set of rules to reduce data redundancy. 1NF ensures every cell has atomic, single values. 2NF ensures all columns depend on the entire primary key, removing partial dependencies. 3NF ensures non-key columns don't depend on other non-key columns, removing transitive dependencies.

interview prep · text extraction

Regex extraction & canonical shortcodes

The tool your Data Normalization actually runs on. Regex finds a pattern in messy text; the shortcode is the one fragment worth keeping.

The anatomy of a raw link

what comes in vs. what matters
https://www.instagram.com/reel/DZ-CmsTJPBC/?stkn=NTc4MTIwNjQ2YQ==
Base path
instagram.com/reel/

The fixed, hardcoded prefix. Same for every reel, regardless of who shared it.

Shortcode
DZ-CmsTJPBC

The unique identifier for this one video. The only variable part worth extracting.

Canonical URL
.../reel/DZ-CmsTJPBC/

Base path + shortcode, rebuilt from scratch. The official version saved to the DB.

Reading the pattern

what each piece of the regex does
instagram\.com\/(?:reel|p)\/([A-Za-z0-9_-]+)
instagram\.com\/

The landmark. Tells the engine "ignore everything until you see this exact text" — without it, Regex would grab the first letters it finds, which is https.

(?:reel|p)

Matches either word, but the ?: makes it a non-capturing group — it's a signpost to walk past, not something to save. Covers both reel and post URL styles.

([A-Za-z0-9_-]+)

The extraction trap. Parentheses create a capture group — whatever matches inside gets saved. The character class accepts letters, digits, underscores, and dashes; + keeps grabbing until it hits a slash or ?.

What match() actually returns

where the shortcode lives in memory
match[0] "instagram.com/reel/DZ-CmsTJPBC" the full match — everything the pattern touched match[1] "DZ-CmsTJPBC" the capture group — only what was inside the ( )

Why rebuild instead of extracting the whole URL

the same video, three different strings

Users paste links from browsers, apps, and tablets — the prefix is never guaranteed to match.

Extract the whole URL → inconsistent

http://instagram.com/p/DZ-CmsTJPBC
www.instagram.com/reel/DZ-CmsTJPBC
https://www.instagram.com/reel/DZ-CmsTJPBC

Extract shortcode, rebuild → identical

https://www.instagram.com/reel/DZ-CmsTJPBC/
https://www.instagram.com/reel/DZ-CmsTJPBC/
https://www.instagram.com/reel/DZ-CmsTJPBC/

Three visually different links, same video — but only one is treated as canonical. Extracting only the shortcode and hardcoding the rest guarantees every entry in the database has the exact same shape, so duplicates get caught every time.

interview prep · backend pipeline

Ingestion & the de-dupe gate

Jargon-heavy on paper. In plain English it's three moves: send, check, save — with a bouncer standing at the door.

The three hops

send → check → save
2.1

Ingestion dispatch — the send

"Ingestion" just means a system taking in new data.

The Flutter app takes the clean URL and throws it over the fence to the Vercel backend with an HTTP request.

HTTPS POST /api/staging/ingest
2.2

Fast de-duplication gate — the bouncer

Before doing any expensive work, ask: "do you already exist?"

The backend checks Firestore for a document literally named after the shortcode. If it's already there, the request gets turned away with an HTTP 409 — no AI calls, no wasted writes.

GET doc(shortcode) → exists? → 409 Conflict
2.3

Staging persistence — the save

"Persistence" just means writing data to disk so it survives a restart.

Only if the gate confirms this is brand new does the backend write it, marked pending — the exact signal that tells the dashboard a fresh video is waiting to be scanned.

setDoc({ url, status: "pending", createdAt })

Gibberish ID vs. natural ID

what makes duplicates physically impossible

Gibberish ID (auto-generated)

7xKp9LqQwERT

Firestore's default. Fine for things like comments — but the same URL could get saved under ten different random IDs with nothing stopping it.

Natural ID (the shortcode)

DZ-CmsTJPBC

An identifier that already exists in the real world. Forcing the document's name to be the shortcode means Firestore literally cannot hold two copies of the same video.

A natural ID doesn't just help you find duplicates faster — it makes the database structure itself prevent them from existing.

Where the regex actually runs

never trust the client

The Flutter app may do a quick client-side cleanup first — nice for speed, but not something to rely on.

The real regex lives in the Vercel backend. If someone skips the app entirely and hits the API directly with a messy link, the backend still sanitizes it before it ever touches the database.

What actually happens on a 409

no crash, no silent delete

Backend checks Firestore: DZ-CmsTJPBC already exists.

Backend stops immediately and sends back HTTP 409 Conflict — a polite refusal, not an error state.

The original document already in the database is untouched. The incoming duplicate is discarded — never written at all.

Flutter receives the 409 and shows a toast: "This Reel is already in the system!"

The duplicate is never saved. The 409 is a shield that protects database quotas and keeps the data clean — it aborts the request, it doesn't crash the system or wipe anything.

interview prep · frontend queue management

Dashboard ingestion & queue coordination

Two rules that keep the dashboard cheap and the AI provider from banning you: fetch a small slice, and process one at a time.

Bounded vs. unbounded — the query itself

"bounded" describes the query, not the data

Unbounded query

5,000 reads

"Get me all pending videos" with no limit. If 5,000 are waiting, Firestore pulls all 5,000 at once — burning that much of the daily quota in one call.

Bounded query

20 reads

"Get me pending videos, but stop after 20." A strict ceiling on how much the query is allowed to pull down at once.

// The limit(20) is the boundary! const q = query( collection(db, "staging"), where("status", "==", "pending"), limit(20) );

Why not onSnapshot instead? It's a live, real-time listener — cool, but every update triggers a new read. On Firebase's free Spark plan (50,000 reads/day), that can burn the whole quota in a few hours. A one-time bounded fetch is a manual "refresh" instead of an always-on connection — it costs a fraction as much and never crashes the app.

The queue lock — single-file execution

why "Scan All" doesn't fire 10 requests at once

Firing several AI requests in the same millisecond gets you an HTTP 429 "Too Many Requests" ban. The fix is a lock that only lets one item run at a time.

1processing
16s cooldown
2processing
26s cooldown
3processing

isAutoProcessingRef — a React useRef acting as a flag. When item 1 starts, it flips to true, like a "register closed" sign.

Single-file execution — item N+1 cannot start until item N has finished every stage.

6-second cooldown — after each item finishes, a mandatory pause gives the AI API time to cool down before the next request.

Together, the bounded query and the queue lock say the same thing to an interviewer: this system scales without breaking rate limits or running up a database bill.

Step 1: engagement scraping

The information-gathering half of the pipeline, split off on its own so a slow scrape can't time out the whole request.

Three hops, one goal: gather the numbers

command → grab → checkpoint
4.1

Scrape trigger — the command

The dashboard tells the backend: wake up, do exactly one job.

:id is the shortcode, and ?step=scrape tells the server "only do the scraping part — leave the AI analysis alone for now."

POST /api/staging/DZ-CmsTJPBC/process?step=scrape
4.2

Extraction & transformation — the data grab

The backend reads the reel's raw HTML and pulls out the numbers that matter.

Username, follower count, view metrics, likes, and the thumbnail's CDN link — enough for the AI step to have something to look at next.

4.3

Staging state update — the checkpoint

Save progress so a crash never means starting over.

Status flips from pending to scraping_done. If the server dies right after, a restart sees that status and skips straight to AI analysis instead of re-scraping.

status: "pending" → "scraping_done"

How the scrape actually works

the real Node.js code
import * as cheerio from 'cheerio'; export async function scrapeInstagramReel(canonicalUrl) { // 1. Emulate a mobile browser so Instagram doesn't block the request const headers = { 'User-Agent': 'Mozilla/5.0 (iPhone; CPU iPhone OS 16_6 like Mac OS X)...', 'Accept': 'text/html,application/xhtml+xml,...' }; // 2. Fetch the raw HTML string over HTTPS const response = await fetch(canonicalUrl, { headers }); const htmlText = await response.text(); // 3. Parse the HTML string into a queryable DOM tree const $ = cheerio.load(htmlText); // 4. Pull the OpenGraph meta tags out of the <head> const thumbnailCdnUrl = $('meta[property="og:image"]').attr('content'); const description = $('meta[property="og:description"]').attr('content'); // 5. Parse likes/comments/username out of the description text const metrics = parseOgDescription(description); return { ...metrics, thumbnailCdnUrl }; }
1

User-agent bypass

A bare fetch looks like a bot and gets a 403 or 429 instantly. Sending a realistic iPhone User-Agent string makes the request look like an ordinary mobile browser.

2

Raw HTML ingestion

The server sends an HTTPS GET to the canonical URL and downloads the entire page — thousands of lines of raw HTML — as one text string.

3

DOM parsing with Cheerio

Node.js can't read HTML like a browser does. Cheerio parses the raw string into a virtual DOM tree so the code can query it with CSS-style selectors — a server-side jQuery.

4

OpenGraph tag mining

Every public post has OpenGraph <meta> tags baked into its HTML so link previews look good on WhatsApp or iMessage. Those same tags conveniently expose the thumbnail and engagement text.

5

String sanitization

A helper regex strips commas and words out of the description text — turning "15K likes, 120 comments - user on..." into clean, structured numbers ready to save.

What each meta tag hands over

OpenGraph selectors, targeted directly
meta[property="og:image"]

The direct CDN link to the video's cover thumbnail — the picture the AI step will look at.

meta[property="og:description"]

A text blurb that happens to contain likes, comments, and the username in one string, ready to be regex-parsed.

Splitting scrape and analysis into separate hops, each saving its own checkpoint, is exactly how production systems survive crashes without losing work — say this line in an interview and it lands.

Step 2: multimodal AI analysis

Four hops: call the AI, survive it failing three times, force its messy reply into clean JSON, then decide.

The four hops

trigger → cascade → parse → gate

Analysis trigger — the command

Same pattern as the scrape step, different query flag.

Multi-provider cascade — the fallback fleet

If one AI provider fails, quietly try the next. Never let the whole request die because of one vendor.

Each provider is wrapped in its own try/catch. A failure logs a warning and falls through to the next provider instead of throwing an error back to the user.

The JSON hunter

why AI replies can't go straight into JSON.parse()

Models often answer with "Here is the JSON you requested: ```json {...} ```" instead of pure JSON. Feeding that straight into JSON.parse() throws a syntax error.

function extractJsonBoundaries(text) { // scan left→right for the first '{', right→left for the last '}' const startIndex = text.indexOf('{'); const endIndex = text.lastIndexOf('}'); // everything outside that range — markdown fences, chit-chat — gets discarded return text.substring(startIndex, endIndex + 1); }

It's a mechanical hunter, not a smart parser — it doesn't understand the text, it just finds the outermost braces and slices between them, guaranteeing JSON.parse() gets a pristine object.

How an image becomes "code"

yes — it really does send 1s and 0s, not a picture

APIs can't attach a JPEG the way a chat app does. JSON is text-only, so the image has to be translated into text before it can travel inside the request.

1 · fetch
image/jpeg, pixels

The server downloads the thumbnail from Instagram's CDN. At this point it's still a normal image file.

2 · ArrayBuffer
[255, 216, 255, 224, ...]

The file format is stripped away, leaving a raw sequence of numeric byte values in memory.

3 · Base64
/9j/4AAQSkZJRgABAQEASABIAAD...

Every 3 raw bytes get re-encoded into 4 safe ASCII characters — a text form that can travel inside a JSON payload without corruption.

4 · sent
{ inlineData: { data, mimeType } }

That giant text string is dropped into the request body and sent to Gemini or Groq, which decode it back into pixels on their end.

async function convertImageToAiPayload(imageUrl) { // Line 1: download the image file from Instagram's CDN const response = await fetch(imageUrl); // Line 2: read it into a raw binary ArrayBuffer — just memory bytes now const arrayBuffer = await response.arrayBuffer(); // Line 3: wrap it in a Node Buffer so the byte numbers are easy to manipulate const nodeBuffer = Buffer.from(arrayBuffer); // Line 4: encode the binary bytes into safe ASCII text const base64String = nodeBuffer.toString("base64"); // Line 5: package it in the exact shape the AI API expects return { inlineData: { data: base64String, // the whole image, now text mimeType: "image/jpeg" // tells the AI how to decode it } }; }

JSON can only carry text, so Base64 is the bridge: raw binary in, safe ASCII out. The AI's servers reverse the exact same steps — decode the text, rebuild the bytes, reconstruct the pixels — before its model ever "looks" at anything.
