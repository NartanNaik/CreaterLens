A mental framework for writing technical architecture documentation, the script to explain it to an interviewer, and answers to follow-up questions.

The Mental Framework: How to think about and create these files

When you need to write technical architecture documentation from a system description, do not try to write it top-to-bottom. Use this four-pass mental model.

1. How to think about the "Request Lifecycle" (Text)

The Goal: Make it so a new developer can trace a bug from a user's screen all the way to the database. The Method: "Follow the Payload."
Mobile→API→DB→Frontend→API→3rd Party→DB→Frontend

  1. Find the Boundaries

    I identified the physical locations data travels through: Mobile → API → DB → Frontend → API → 3rd Party → DB → Frontend.

  2. Identify the Verbs

    At each boundary, what happens? I specifically looked for terms like "extracts," "computes," "fetches," and "parses" in your breakdown. I labeled these Data Transformations.

  3. Track the State

    How does the database know what step we are on? I noticed the status field changing (pending → scraping_done → analyzed). I anchored the phases around these state changes.

  4. Expose the Fragility

    A lifecycle document is useless if it only describes the "happy path." I explicitly pulled the Failure-Mode Matrix into the lifecycle trace so developers know exactly where a 409 or a 429 will occur.

The Goal: Give the team a map of the territory so they know what systems talk to what, and where the danger zones are. The Method: "Nodes, Edges, and Explosions."

The Interview Script

An exact script to explain your documentation thought process. It positions you as an organized, systems-level thinker who writes documentation to solve real engineering problems (like debugging and onboarding) rather than just checking a box.

The Hook

Start here when asked about your documentation style or how you designed the architecture

"When I need to document a complex system like CreatorLens AI, I don't just write top-to-bottom. My goal is to create artifacts that actually help developers debug production issues. To do that, I use a specific mental framework to build both the written lifecycle and the visual architecture diagram."

Part 1: The Written Trace ("Follow the Payload")

For the written documentation, my objective is to make it so a new developer can trace a bug from the user's screen all the way to the database. My method for this is called 'Follow the Payload,' and I write it in four passes.

First, I find the boundaries. I identify every physical location the data travels through, from the Mobile client, to the API, to the database, out to third-party services, and back.

Second, I identify the transformations. Every time data crosses a boundary, I explicitly document the verb. Is it being extracted, computed, or parsed?

Third, I track the state. I map out exactly how the database knows what step we are on, anchoring the documentation around state changes, like moving from pending to scraping_done.

Finally, I expose the fragility. Documentation is useless if it only describes the happy path. I explicitly map out the failure modes at every network hop so a developer knows exactly where a 409 Conflict or a 429 Rate Limit will occur.

Part 2: The Visual Diagram ("Nodes, Edges, and Explosions")

Once the written trace is done, I translate it into a visual map. My approach here is what I call 'Nodes, Edges, and Explosions.'

For the Nodes, I group the system into strict categories: Clients, APIs, Databases, and External Dependencies.

For the Edges, I connect those nodes chronologically based on the written lifecycle, numbering every arrow so it reads as a sequence flow rather than just a web of lines.

And for the Explosions, I take those failure modes I identified earlier and attach them directly to the visual nodes. If Instagram's CDN changes its DOM structure, the diagram shows exactly which node breaks.

The Wrap-Up

Your core engineering philosophy

"Ultimately, whenever I'm architecting or documenting a new feature, I force myself to answer three questions: Where does the data start? What is the exact payload at every network boundary? And if the server loses power at this exact millisecond, what happens?

I've found that if I write down the answers to those three questions, the resulting documentation is practically bulletproof."

Q: Should these files be created before the project, or while building it?

The Answer for Your Understanding

You create these files in stages: a little bit before, a little bit during, and the final polish after. If you try to write the exact, detailed trace before you write any code, you will waste time because your plan will change once you start hitting real-world bugs. Here is how it actually works in practice:

  • BeforeThe Sketch. You draw a rough version of the Mermaid diagram (just the nodes and edges) before writing code. This helps you figure out what you actually need to build.
  • DuringThe Messy Updates. While you are coding, you discover things. For example, you realize the AI API fails sometimes, so you add a fallback. When you do that, you jot down a quick note in your lifecycle trace: "Added fallback to Groq here."
  • AfterThe Final Polish. Once the code is working and ready to merge, you clean up the request-lifecycle.md and the current-architecture.mermaid files so they perfectly match the actual code you wrote, not the code you guessed you were going to write. This is called "as-built" documentation.

The Answer to Tell the Interviewer

"I treat architecture documentation as a living process that happens in three distinct phases: before, during, and after the build.

Before I write a single line of code, I draft a lightweight version of the architecture diagram. I map out the core nodes and the expected edges. This acts as my technical spec or RFC, allowing me to validate the general data flow and spot obvious bottlenecks early.

During the build phase, the documentation becomes a scratchpad. As I implement the code, I inevitably hit real-world constraints, like discovering a third-party API rate limit or realizing I need an extra database state for queue management. When I write the code to handle those edge cases, I immediately update the 'Failure Modes' section of my documentation so the context isn't lost.

After the feature is complete, but before the PR is merged, I do the final polish. I update the request lifecycle trace and the Mermaid diagram to reflect the 'as-built' system. I consider these artifacts part of my Definition of Done. This ensures that the documentation merged into the main branch represents exactly what is running in production, making it immediately useful for the next developer who needs to debug the system."

Q: What are we doing now, and why? (The Failure Lab)

The Answer for Your Understanding

We are about to play the villain against your own codebase. We are going to systematically break three critical pieces of your app (the AI key, the scraper, and the database) and just watch it burn.

  • AI key
  • Scraper
  • Database

What we are doing

We are running a manual "Chaos Engineering" lab. Instead of writing code, you are going into your .env files and intentionally putting in fake API keys and bad project IDs. Then, you are going to try to use the app normally and take notes on exactly how and where it crashes.

Why we are doing it

Because you need to know if your app fails silently or loudly.

Loud failure (Good)The app crashes, the UI says "API Error," and nothing is written to the database. You know exactly what went wrong.
Silent failure (Bad)The app spins forever, the user has no idea what's happening, and your database gets clogged up with "half-finished" staging documents that will sit there forever.

By breaking the system on purpose right now, you are mapping out exactly where your app is fragile so you know exactly what error-handling code you need to write in the next phase.

The Answer to Tell the Interviewer

"To ensure the architecture was actually resilient, I conducted a targeted failure mapping exercise, essentially a manual chaos engineering lab.

What I did: I systematically severed critical dependencies in the pipeline to observe the system's behavior under duress. I temporarily invalidated the Gemini API key, fed malformed URLs to the scraper module, and deliberately misconfigured the Firestore environment variables. For each scenario, I submitted a standard payload and traced the execution path.

Why I did it: I needed to audit the blast radius of external failures. My goal was to determine if the system failed gracefully, with visible, actionable errors and clean database rollbacks, or if it failed silently, leaving hanging UI states and orphaned, partial writes in the database.

By mapping these failures before attempting to write any recovery logic, I was able to build a highly precise, evidence-based backlog for system reliability. It allowed me to move beyond guessing where the system was fragile and actually prove how it handled catastrophic downstream outages."

Q: Should we do this before, during, or after the project build?

The Answer for Your Understanding

You do this during the build, specifically right in the middle.

Think of it as a checkpoint. You do it exactly after you get the "happy path" working perfectly, but before you write any error-handling code.

You can't do it before you start the project because there is no code to break. You shouldn't do it after the project is completely finished because going back and ripping out finished architecture to fix deep database issues is a massive headache.

The workflow is always:

  1. Build the core pipeline so it works when everything goes right.
  2. Run this Failure Lab to watch how it dies when things go wrong.
  3. Write the specific fixes for the holes you just found.
  4. Finish the project.

The Answer to Tell the Interviewer

"I integrate this failure mapping during the development cycle, specifically immediately after establishing the core 'happy path' of a new feature.

Waiting until the very end of a project to test for failure is an anti-pattern. If you discover a fundamental flaw in how your database handles partial writes on the final day, retrofitting that fix into a finished codebase is incredibly expensive and risky.

Instead, I use this exercise as a phase-gate. Once the main pipeline successfully processes a clean payload, I immediately pivot to chaos testing. Finding exactly where the system bleeds dictates the precise error-handling and recovery logic I need to write next. This ensures I am hardening the system based on actual observed behavior, rather than just guessing what might break before I push to production."

What the Failure Lab Uncovered

The Answer for Your Understanding

When you simulate these failures in a standard Node.js, React, and Firebase stack, you almost always uncover a mix of "zombie" database records and silent frontend hanging. Here is exactly what you would have faced during this lab based on your architecture:

Test 1: Breaking the AI (Invalid Gemini Key)

When you invalidated the key, the Gemini API returned a 401 Unauthorized. Because the AI processing happens in step 2, the document had already passed the scraping phase.

The Blast Radius: The backend threw an error when the AI cascade failed. Because there was no specific rollback logic, the Firestore document was left completely abandoned with status: "scraping_done". On the React dashboard, the item just sat in the queue spinning indefinitely because the frontend was waiting for the status to change to analyzed, which never happened. This is a classic silent failure causing database bloat.

Test 2: Breaking the Scraper (Bad URL)

When you fed it a broken URL, the RapidAPI scraper returned a 404 Not Found or an empty object.

The Blast Radius: The next line of your backend code tried to read data.thumbnailUrl. Since data was undefined, Node.js threw a fatal TypeError: Cannot read properties of undefined. The Vercel serverless function crashed immediately, returning a generic 500 Internal Server Error. The staging document was left stuck on status: "pending".

Test 3: Breaking the Database (Invalid Firebase Auth)

When you messed up the Firebase project ID, the Firebase Admin SDK failed to authenticate.

The Blast Radius: When the mobile app tried to hit the POST /api/staging/ingest endpoint, the database create() method threw an auth error. The backend crashed before it could even send a proper JSON response back to the client. The mobile app either showed a generic network timeout or crashed entirely. No document was ever created.

The Takeaway: You learned that your system lacks a "garbage collection" routine for zombie documents, and that unhandled API rejections can crash your entire serverless function instead of failing gracefully.

The Answer to Tell the Interviewer

"During the build phase, I ran a manual failure lab to map the blast radius of external dependencies. What I found was a textbook example of why testing the happy path isn't enough.

First, I temporarily invalidated my Vision AI API keys. I discovered that when the AI cascade failed, the backend threw an exception, but it left the Firestore document permanently stuck in a scraping_done state. Because the React frontend was polling for an analyzed status, the UI just spun indefinitely. It was a silent failure that would have eventually bloated the database with zombie records.

Next, I fed the scraper a malformed URL. The third-party scraper returned an empty payload, which caused an unhandled TypeError in Node.js when the system tried to parse the thumbnail. This crashed the Vercel serverless invocation entirely, returning a hard 500 error to the client instead of a graceful rejection.

Finally, I deliberately misconfigured the Firestore environment variables to simulate a database outage. The ingestion endpoint failed immediately, proving that I needed strict error boundaries on the mobile client so the app wouldn't just hang if the backend was unreachable.

Running this exercise gave me a highly specific backlog. Instead of guessing what might break, I had empirical proof that I needed to implement database rollback transactions for orphaned documents, strict null-checks on external API payloads, and proper HTTP error codes so the React dashboard could actually tell the user when a job failed."

Mass Upload: The JSON Bulk Import

A second way into the system. An admin pastes a saved-posts-backup-export JSON (exported by a browser extension) and the app stores the data in one go. The export has an images array and a videos array; each item carries postUrl, thumbnail and a metadata object with owner, caption, likeCount and hashtags.

What this JSON means for the architecture

The Answer for Your Understanding

What you pasted is a structured data export (likely from a Chrome extension that exports saved Instagram posts). This is a massive shortcut for your system. Here is exactly how it fits into your architecture:

It skips the Scraper (saves time and money). Normally, your app takes a URL, then calls RapidAPI to get the thumbnail, caption, and likes. But this JSON already has the owner (username), thumbnail, likeCount, and caption. When you upload it, your backend can inject these items directly into the staging database with status: "scraping_done", completely bypassing the fragile RapidAPI step.

It solves the 1-by-1 bottleneck. Sharing from a phone is slow. This JSON allows an admin to upload 100 profiles in one second.

Two limits, two layers of chunking. A big JSON runs into two different ceilings, so the work is split in two places. Layer 1 (browser): Vercel rejects request bodies over about 4.5MB, so GarbageEater.jsx sends the data to /staging/bulk-import in chunks of 50. Layer 2 (backend): Firestore allows at most 500 writes in one batch, so the endpoint writes each incoming chunk to Firestore in its own batch, well under that cap, and counts what was added vs. skipped. Because each request is small, it also finishes fast, well inside the serverless time limit. Verify the exact batch size in your stagingController.js before quoting a number.

Once they are batch-written, the React dashboard's queue lock picks them up and starts firing them directly to the AI cascade (step=analyze).

The Answer to Tell the Interviewer

"While the mobile share intent is great for one-off profile discoveries, I realized that admins needed a way to ingest hundreds of creators at once. To solve this bottleneck, I built a bulk-import pipeline that accepts a structured JSON payload directly in the React dashboard.

This JSON payload is typically generated via a browser extension that exports saved Instagram posts. What makes this architecture highly efficient is that the payload already contains the critical metadata we need: the creator's username, the high-res thumbnail URL, captions, and engagement metrics. Because of this, I engineered the ingestion endpoint to detect bulk payloads and completely bypass the RapidAPI scraping step. The records are written to the staging queue with their state immediately advanced to 'scraping_done', saving us third-party API costs and massive amounts of processing time.

The main technical hurdle was that a large import hits two different limits, so I chunk at two layers, each protecting a different constraint. The first limit is the transport: Vercel rejects request bodies over roughly 4.5MB, so a 2,000-profile paste sent in one POST would fail with a 413. The browser therefore slices the payload into chunks of 50 and sends them sequentially. The second limit is the database: Firestore caps a batch write at 500 operations, so the backend writes each incoming chunk as its own atomic batch, far below that ceiling, and returns how many records were added versus skipped as duplicates.

I chose chunking on the client rather than on the backend alone because the client is the only place that can fix the 413 problem; once the body is too big, the server never sees it. Small chunks also keep each serverless invocation short, so none of them risks a timeout. They also give the admin real progress feedback ('batch 3 of 40') and make failures cheap: if one chunk fails, the others are already saved and the import is safe to re-run, because the natural document IDs make every write idempotent.

Once the batch import completes, the React dashboard's queue orchestrator takes over, sequentially feeding the pre-scraped thumbnails directly into the AI Vision cascade for demographic analysis."

The frontend component: GarbageEater.jsx

The Answer for Your Understanding

This is the React frontend component (affectionately named GarbageEater) that accepts the massive JSON payload. Step by step:

  • IngestIngestion and flattening. It parses the raw JSON string you paste in and merges the images and videos arrays into one giant list (rawItems).
  • DedupeDeduplication (frontend). It uses a Map keyed by postUrl to strip out duplicate posts before they hit your server. If a reel is in the JSON twice, it only gets processed once.
  • TransformData transformation. It maps the raw Instagram export schema into your system's payload format ({ url, username, thumbnailUrl, caption }). Missing data is handled gracefully (e.g., item.metadata?.owner || "Unknown").
  • ChunkThe chunking logic. This is the most important part. Serverless functions (like Vercel) have strict payload limits (usually 4.5MB). If you send 2,000 high-res URLs at once, Vercel rejects it with a 413 Payload Too Large. This code splits the array into chunks of 50 items and sends them sequentially via a for loop with await.
  • ReportUI feedback. It updates the status message in real time ("Importing batch X of Y...") and finally reports how many were added vs. skipped (which the backend determines based on what's already in Firestore).

The Answer to Tell the Interviewer

"To handle the bulk ingestion of JSON payloads on the frontend, I built a dedicated React utility component.

When an admin pastes an Instagram data export into the UI, the component first parses the JSON and flattens the image and video arrays. Before sending anything to the backend, it performs a client-side deduplication pass using a Map structure keyed by the post URL. This ensures we aren't wasting bandwidth sending duplicate records to the server.

The biggest constraint I had to engineer around was Vercel's 4.5MB payload limit for serverless functions. If an admin pasted a JSON file containing thousands of records, sending it in a single POST request would result in a 413 Payload Too Large error.

To mitigate this, I implemented a client-side chunking algorithm. The React component slices the sanitized payload into batches of 50 records. It loops through these chunks and awaits the POST request to the /staging/bulk-import endpoint sequentially. During this process, it provides real-time progress feedback to the user, updating the UI to show which batch is currently processing, and finally returning an aggregate count of how many records were successfully queued versus how many were skipped by the backend's duplication checks."

The backend controller: stagingController.js

The Answer to Tell the Interviewer

"This file, stagingController.js, acts as the central orchestrator for the entire ingestion and processing pipeline. Rather than just serving as a basic CRUD controller, I engineered it specifically to handle race conditions, third-party API rate limits, and strict database constraints.

Security. I implemented SSRF (Server-Side Request Forgery) protection. The safeMediaUrl helper uses a strict regex, MEDIA_HOST_REGEX, to ensure the server only ever fetches thumbnails from approved Instagram or Facebook CDNs. This prevents malicious users from submitting arbitrary URLs during bulk import and forcing my backend to ping unauthorized network addresses.

Data integrity and deduplication. I used a natural ID strategy. When a Reel enters the staging queue, the stageReel function extracts the canonical shortcode and combines it with the creator's sanitized username to form the document ID. I use Firestore's atomic create() method. If two admins try to ingest the same Reel at the exact same millisecond, the database rejects the duplicate at the transaction level, completely preventing race conditions. I also check incoming handles against an in-memory Bloom filter for ultra-fast deduplication before we even spend database read operations.

Core execution. The core logic lives in processStagingItemController, which I split into two discrete API query steps: ?step=scrape and ?step=analyze. Decoupling these allows me to handle third-party failures independently. If the AI service throws a 429 Rate Limit error, the controller catches it via the isRateLimitError helper and returns a 429 to the client, allowing the React dashboard to retry gracefully without losing the previously scraped data. When the AI analysis succeeds, the code runs a regex gate, REJECT_ACCOUNT_REGEX, instantly auto-deleting the document if the account is flagged as male or a brand. If it passes, I use FieldValue.delete() to cleanly strip the tempScrapeData from the document while writing the final demographic fields, keeping the payload lean.

Approval pipeline. I had to architect around Firestore's strict system limits. The single-item approval uses db.runTransaction to guarantee that moving a document from the staging queue into the production profiles collection is perfectly atomic. For bulkApproveStagingItemsController, Firestore hard-limits batch writes to 500 operations. Because a single approval requires two operations (writing the new profile and deleting the staging item), I built a custom chunking algorithm that strictly batches 200 items at a time, resulting in exactly 400 operations per batch. This ensures that even if an admin approves a massive queue, the serverless function executes without ever hitting the database ceiling."

Q: Walk me through what happens when a user shares a post to your app.

Flutter share→Vercel API→Firestore: pending→React queue→RapidAPI→scraping_done→AI cascade→analyzed→profiles

The Answer to Tell the Interviewer

"It's a four-stage serverless pipeline designed to handle rate limits, prevent data duplication, and gracefully manage third-party API failures.

First, it starts on the mobile client. When a user triggers the native OS share intent from Instagram, my Flutter app intercepts the payload, strips out the tracking parameters, and extracts the canonical shortcode. It sends that normalized URL to my Vercel Node.js backend.

To handle deduplication immediately, and cheaply, the backend uses that shortcode to generate a natural document ID. It attempts an atomic create() operation in Firebase Firestore. If the Reel has been submitted before, Firestore throws a 409 Conflict, and we drop the request right there to save database writes. If it's new, it drops into a staging collection with a 'pending' status.

Next is the queue coordination. Over on the React admin dashboard, the frontend polls this staging queue. To protect our Firestore free tier, I specifically bounded this query to 20 documents instead of using expensive real-time listeners. The React app takes a local lock on the oldest item and orchestrates a two-step processing pipeline, enforcing a strict 6-second cooldown between items so we don't trigger burst rate limits on our downstream APIs.

The first processing step is scraping. The backend hits a RapidAPI endpoint to pull basic engagement metrics and the raw thumbnail URL, updating the document status to 'scraping_done'.

The second step is the multimodal AI analysis, which was the hardest part to engineer. The backend converts that thumbnail into a Base64 payload and sends it through a multi-provider cascading pipeline. It tries Google Gemini first. If we hit a 429 quota limit, it automatically falls back to Groq, then OpenRouter, and finally Pollinations. Because LLMs often return chatty text, I wrote a custom 'JSON Hunter' parser that uses boundary indices to extract the exact demographic data, guaranteeing strict JSON parsing.

Finally, the system runs a regex-based demographic gate. If the AI determines the account is a brand or outside our target demographic, the system rejects it. If it passes, it sits in the dashboard as 'analyzed'. When an admin clicks approve, the record is migrated to the production profiles collection, and the username is added to an in-memory Bloom filter on the frontend to drastically speed up any future duplicate checks."

Q: Why is the pipeline asynchronous instead of one long function call?

The Answer to Tell the Interviewer

"I designed the pipeline asynchronously to solve two major infrastructural constraints: serverless execution limits and third-party rate limiting.

First, the backend runs on Vercel serverless functions, which have a strict execution timeout. If I combined the Instagram HTML scraping, the image conversion, and the Vision AI cascade into a single synchronous function call, it would frequently breach the timeout limit and crash. By decoupling the architecture into discrete step=scrape and step=analyze endpoints, I guarantee that each network hop completes well within the serverless limits.

Second, this asynchronous split provides critical failure isolation. Third-party APIs are inherently fragile. If the pipeline was one long function and the AI provider threw a 429 Rate Limit error at the very end, the entire invocation would fail. I would lose the extracted data and have to re-scrape Instagram, which risks an IP ban. By splitting the state, if the AI cascade fails, the document safely remains in the database with a scraping_done status. The React client can then gracefully retry just the analysis step without wasting bandwidth or burning our scrape quotas."

Q: Why did you use Vercel for the backend deployment? Why not Render?

The Answer to Tell the Interviewer

"I chose Vercel over Render because Vercel was a much better architectural fit for our bursty, stateless workload and eliminated substantial operational overhead.

First was deployment architecture and zero-CORS routing. By using Vercel, I could co-locate the React frontend and the Express serverless endpoints within a single monorepo. Using vercel.json rewrites to proxy all /api/* traffic directly to the serverless runtime meant the entire app runs under a single origin. This completely eliminated CORS preflight latency on critical network paths and kept CI/CD unified under one pipeline, rather than orchestrating two separate platforms.

Second was cold start latency and user experience. Render's free or entry-level web services put idle containers to sleep after 15 minutes of inactivity, which causes a 30 to 50-second spin-up penalty when a new request arrives. For an app driven by a native mobile share intent, a 40-second hang is unacceptable: the OS intent could time out, or the user would assume the app was broken. Vercel's serverless functions, on the other hand, have sub-second cold starts, ensuring immediate responsiveness when an admin shares a Reel.

Finally, it came down to workload characteristics. Render is an exceptional choice when you have persistent WebSockets, background cron daemons, or long-running worker threads. But because I specifically architected CreatorLens into decoupled, discrete HTTP requests (step=scrape and step=analyze) that each finish in a few seconds, the backend is strictly event-driven. Running a dedicated 24/7 container on a service like Render to handle occasional bursts of reels is inefficient. Vercel's serverless execution model gave me automatic scaling to zero, rapid horizontal concurrency, and zero server maintenance."
